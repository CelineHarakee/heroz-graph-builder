# Phase 6 D1 — Reliability & Failure Model

Heroz should either complete an operation correctly or fail in a known, safe,
and eventually observable way without corrupting authoritative state.

`createReliabilityFailure` is a pure internal metadata factory, not an execution
wrapper or a classifier of engine results. It requires category, component,
operation, message and stateStatus. `retryable` defaults to false. Only an
operation that has explicitly established safe replay may supply true; this is
metadata, never authorization for automatic retry execution.

| Category | Required handling by the operation owner |
| --- | --- |
| INPUT_FAILURE | Reject before processing where possible; no automatic retry. |
| STATE_FAILURE | Stop safely; never change authoritative state to force success. |
| DEPENDENCY_FAILURE | Stop the affected operation; no silent fallback. |
| TIMEOUT_FAILURE | Stop waiting; verify uncertain writes before replay. |
| INTERNAL_FAILURE | Fail closed; do not improvise intelligence behavior. |
| PARTIAL_FAILURE | Preserve completed work; require state-aware recovery, not blind restart. |

State is explicit, never inferred from category. UNCHANGED means authoritative
state is known not to have changed. COMMITTED means the intended authoritative
state committed, even if a later dependent step failed. PARTIAL describes some
completed work. UNKNOWN means commit status cannot safely be determined.
Timed-out writes remain UNKNOWN until authoritative state is verified.

The returned record is frozen and has enumerable category, component, operation,
message, retryable and stateStatus. Optional cause and diagnosticContext remain
accessible internally but are non-enumerable. They retain caller-owned references;
D1 neither invokes nor mutates them. Context may describe completed steps and
canonical source/job identities. Do not put new behavioral evidence in recovery
metadata. No IDs, timestamps or stack traces are generated by this factory.

The entire record, including message, is internal. Non-enumerable diagnostics are
not a substitute for the API boundary. Pass failures through the existing
`api/apiResponse.errorResponse`: an internal record yields the existing safe 500
INTERNAL_ERROR response. Known public errors still use the existing ApiError.
No category-to-HTTP mapping or public envelope change is introduced.

## Existing authoritative recovery boundaries

- MongoDB remains authoritative. Preserve completed authoritative writes if a
  subsequent step or graph synchronization fails; no automatic rollback.
- Interaction recovery retains the original interaction/source identity.
  Existing learning event normalization, idempotency checks and transactional
  persistence protect replay. Infrastructure replay is not new learning evidence.
- Question-answer integration already derives stable source IDs from question
  history, decision type and target. Reuse these identities. QuestionHistory
  becomes ANSWERED only under the existing successful-learning contract.
- Existing graph queue jobs keep their logical identity. PROCESSED/FAILED queue
  status and existing learning APPLIED/IGNORED/FAILED outcomes remain separate
  domain contracts; the new state statuses do not replace them.
- Partial failure implies neither rollback nor replay. D1 implements no recovery,
  distributed transactions, retries, timers, observers or queue changes. Existing
  operation-specific retry behavior is not modified or broadened.
- Empty recommendations, No Question, legitimate suppression and successful
  duplicate suppression remain valid outcomes. Nothing automatically wraps or
  reinterprets these results as failures.

Later deliverables may consume this representation. D1 adds no observability or
recovery infrastructure and changes no recommendation, learning or question logic.
